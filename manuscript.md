# The Client as Interface Specification: API Attack Surface Recovery and the Validity of Negative Results in Web Security Assessment

**Hasan Flayyih Abdullah**
**Working manuscript prepared:** 1 October 2026
**Status:** Methodology paper with an accompanying experience report; not peer reviewed

## Abstract

Assessment is effective against software whose source can be read, because the hypothesis comes from the system itself and can be refuted before anything is sent; a web server publishes no source, so the hypothesis must come from outside it and a negative result has no established meaning.

A server is reachable only through its interface, and the client calling it is delivered in full to every browser, so the client is a recoverable specification of that interface: paths, methods, body schemas, identifier encodings. For the vulnerability classes the OWASP API Security Top 10 (2023) ranks highest — defined by what a server accepts from a caller rather than by how it computes — that specification suffices both to form a hypothesis and to confirm it, without being equivalent to the implementation.

The principal contribution is a consequence for measurement: the specification is what makes a request well-formed, so a malformed request is observationally indistinguishable from an enforced authorization boundary, and a procedure recovering paths without identifier encodings and body schemas produces negatives that are void rather than informative while being unable to detect it.

We specify the procedure and its five validity controls, report its record across 45 authorized production targets, and measure the extractor against published OpenAPI specifications on three open-source applications, two held out under thresholds fixed in advance.

Extraction recovers 98.8, 62.2 and 82.8 per cent of the paths literally present in each client, so recovery is itself incomplete wherever a client builds paths at runtime. The heuristic nominating attack surface is 32.9 per cent precise and admits 9.5 per cent of the interface its client encodes. Replacing it with call-site evidence reaches the full extraction ceiling on all three applications; precision and the per-route evidence tier do not generalize, moving in opposite directions across clients. On the third application precision is not measurable at all, its client being code-generated from the specification serving as ground truth, and the apparent success is reported as an invalid measurement.

The neglected problem in this setting is therefore not the recovery of attack surface but the establishment that a result measured against it is valid rather than void.

**Keywords:** measurement validity; web application security; API attack surface enumeration; client-side artefact analysis; authorization testing; broken object level authorization; research methodology

## 1. Introduction

Recent results show that language-model agents can find and exploit vulnerabilities in software whose source code they are allowed to read [1,2]. That setting supplies the property that makes human code review work: the implementation is visible, so a hypothesis can be formed from the code and refuted by reading further, before anything is executed. The hypothesis comes from the system under test, and refuting it is cheap.

Web testing appears to remove that property. The server code is not published. What is visible is a rendered page and whatever requests a given session happens to send. Where the structure of the interface is not known in advance, requests must go out before it is known, and the hypothesis then comes from outside the system rather than from it.

**This paper does not argue that one discovery method yields more than another, and it reports no comparison of yield.** Its subject is what a recovered interface specification entitles an assessor to conclude, and under what conditions a result measured against it is valid rather than void. We argue that the property above is not removed but moved, and that locating it correctly changes what AI-assisted web testing can establish. The argument rests on how modern web applications are built, not on any capability of a particular model: the server can only be reached through the application's interface, and the client that calls that interface is delivered in full to every browser. Whatever the client must encode to build a well-formed request is therefore available by reading it.

Section 2 states what each setting makes visible, and declines the claim that the two are equivalent. Section 3 gives three arguments that the client is a sufficient source for a specific and consequential set of vulnerability classes; Section 3.3 is the paper's main contribution, and it concerns the validity of measurement rather than the yield of discovery. Section 4 sets out the procedure and Section 5 the controls it requires. Section 6 reports what the procedure recorded, and Section 6.1 reports a dictionary-enumeration pilot whose budgets were never matched, explaining why it is not a control arm.

Section 6.2 then turns the paper's own instrument on itself, in four steps. It commits in advance to reporting the measurement whichever way it falls; it measures the extractor against a published specification and obtains a poor result; it works through what that result implies for the figures reported in Section 6, including the correction it forces; and it repairs the classifier the measurement indicted, then evaluates the original and repaired rules on three applications, two of them held out, against a criterion fixed before the measurement. Sections 7 and 8 cover threats to validity and prior work, where endpoint recovery from client code is already established and this paper's narrower contribution is positioned against it. Section 9 concludes and states the five extensions the limitations of Section 7 call for.

## 2. Observability in the two settings

A methodology paper that claims to know more than its method can show is easy to refute. The comparison therefore begins by conceding what client recovery does not supply.

**Source inspection renders the implementation observable.** The assessor observes the authorization predicate itself, data flow from entry point to security-relevant sink, parsing and encoding decisions, trust assumptions encoded in control flow, and internal services exposed through no public interface. A defect whose nature is computational — untrusted input reaching a query constructor, unsafe deserialization, an invariant violation internal to a transaction — is observable by reading.

**Client recovery renders the interface specification observable.** The assessor recovers which routes exist, which methods each accepts, the schema of each request body, the field identifiers the client transmits, the identifier encoding each route expects, the headers conveying authentication state, and frequently the application's complete route table. None of this renders the server-side computation observable. The authorization predicate is not observable; only its effects are.

These are distinct categories of knowledge and the paper does not equate them. What follows is a narrower claim, and the narrowness is what makes it defensible: a claim that the client substitutes for the source in general would be false, and would be refuted by a single injection defect. A claim that the client suffices for the classes defined by what a server *accepts* can be argued and, as Section 6.2 shows, measured.

## 3. Sufficiency of the interface specification for the highest-ranked vulnerability classes

### 3.1 The client is the invoking party and is distributed in its entirety

A web application accepts input exclusively through its interface. Every request the application itself issues is therefore constructed within client code — and the application cannot work unless that client is delivered to whoever is using it, which includes the assessor. In client-rendered architectures this is concrete: the deployed bundle contains the request-construction logic, commonly in the form of a generated API client, and typically a route manifest enumerating views together with the resources each retrieves.

This is a structural property rather than an incidental disclosure remediable by improved minification. Code that must construct a request must encode what the request requires. Identifier minification renames bindings; it does not eliminate the literal path, the method, or the field identifiers the server will parse. The property is a necessary precondition of the argument, and Section 7 states the architectures in which it does not hold.

### 3.2 The vulnerability classes determined by the interface

The classes the standard interface taxonomy ranks highest are determined by what a server accepts from a caller rather than by how it computes a result. The ranking is not this paper's assertion: the OWASP API Security Top 10 (2023) places broken object level authorization first, broken object property level authorization third, and broken function level authorization fifth [3]. Stated against that taxonomy and the corresponding CWE entries [4]:

| Class | Taxonomy | How the test is run |
|---|---|---|
| Broken object level authorization | API1:2023; CWE-639, *Authorization Bypass Through User-Controlled Key* | Transmit a reference to a non-owned object as a subject lacking entitlement |
| Broken object property level authorization, including mass assignment | API3:2023; CWE-915, *Improperly Controlled Modification of Dynamically-Determined Object Attributes* | Inject a field the client never transmits, then retrieve the object as a second subject |
| Broken function level authorization | API5:2023 | Invoke a privileged route as a subject holding a lesser role |
| Unrestricted access to sensitive business flows | API6:2023 | Invoke a flow outside the sequence the interface imposes |
| Workflow and state-transition enforcement failure | CWE-841, *Improper Enforcement of Behavioral Workflow* | Execute a transition from a state that should preclude it |
| Absent server-side enforcement of a client-side constraint | CWE-602, *Client-Side Enforcement of Server-Side Security* | Transmit a request violating a constraint the client enforces |
| Undocumented or unmanaged interface inventory | API9:2023, *Improper Inventory Management* | Enumerate routes absent from documentation and observed traffic |

The rows are not mutually exclusive, and the paper does not treat them as a partition: API6:2023 and CWE-841 overlap wherever a sensitive flow is also a state machine, and CWE-639 and API1:2023 describe the same defect at different levels of abstraction. The table enumerates test operationalizations, not disjoint categories.

For each entry, the confirming evidence is a request together with a contrast across subjects, and no element of that evidence requires the implementation. Establishing that one tenant retrieves another tenant's records requires a well-formed request and two subjects; source inspection would explain *why* the predicate is absent, but is not required to establish *that* it is absent. This delimits the claim: the interface specification is sufficient here and insufficient for injection and memory-safety classes, where the defect is computational.

API9:2023 deserves separate mention, since it is the condition the recovery procedure directly addresses: an interface inventory that is incomplete with respect to the deployed surface. Recovery from client artefacts is an enumeration method for precisely the surface this class describes.

### 3.3 The specification determines request well-formedness, and a malformed request is not distinguishable from an enforced boundary

This proposition concerns measurement validity rather than discovery, and is the strongest ground for inspecting the client.

A test constitutes evidence only if its legitimate instantiation succeeds — the positive control condition formalized in Section 5. Where a route receives an identifier in an incorrect encoding, it refuses the request, including when the requesting subject is the rightful owner. The response is observationally equivalent to a correctly enforced authorization boundary. The assessor records a negative result, and the route was never in fact exercised.

The structure of the problem is a two-by-two, and the whole argument is that two of its four cells emit the same observation.

| | Request is well-formed | Request is malformed |
|---|---|---|
| **Owner arm** | 2xx — positive control satisfied | 4xx |
| **Non-owner arm** | 4xx — **boundary enforced; the negative is informative** | 4xx — **void, and indistinguishable from the cell above** |

The lower-right cell is the failure. Nothing in the response separates it from the lower-left cell, because the server's refusal of an unparseable request and its refusal of an unauthorized one are the same event as far as the assessor can observe: a status code and an error body, emitted before any authorization predicate was necessarily reached. The only cell that distinguishes them is the upper-left one. A positive control is therefore not good practice attached to a test; it is the condition under which the test has a result at all, and its absence does not degrade the measurement but removes it.

Three consequences follow, and the third is the one most easily missed.

First, the failure is silent by construction. A procedure in the lower-right cell produces output in the expected shape, at the expected rate, and records it as coverage. There is no error to notice and no anomaly to investigate.

Second, the failure is systematic rather than random. An encoding recovered incorrectly is recovered incorrectly for every subject, every identifier and every repetition, so the void negative is stable under re-testing. Stability is ordinarily read as reliability, which is precisely the wrong inference here.

Third, **testing under multiple identities is necessary and is not sufficient.** The contrast between a legitimate and an illegitimate caller is what makes an authorization defect observable at all, and specification-driven multi-identity scanners are built on that contrast [13]. But a malformed request is malformed in every arm of the contrast simultaneously. Adding identities multiplies the rows in the lower-right cell without moving any of them left. What moves a row left is the recovered encoding, and nothing else does.

Instances of this failure recur and are not atypical. Identifiers belonging to one resource type, supplied to a route expecting another, produce a uniform refusal across all subjects. A route requiring a type-prefixed identifier may be adjacent to sibling routes requiring the unprefixed numeric form, because the invoking code strips the prefix for one and not the others. A uniform refusal across both the owner and the non-owner arm presents as a permission predicate and in fact constitutes a malformed request on both arms.

Neither dictionary enumeration nor crawling resolves this, as both operate on the syntactic form of a path rather than on the contract of its invoking code. Inspection of the invoking code resolves it directly, the encoding being present in the construction logic. The operational rule follows: **where the owner arm is refused, the identifier encoding is to be suspected before any inference is drawn concerning the route.**

The same reasoning governs request bodies. Knowledge of the fields the client transmits is the precondition for injecting a field it does not transmit, which constitutes the entirety of the API3:2023 test. Absent the schema, there is no principled basis for selecting an injection candidate.

A worked instance from the corpus of Section 6 illustrates the dependency, stated without identifying the programme. A registration endpoint on a multi-tenant storefront platform accepted a boolean field governing whether the newly created account required email activation. The field was constructed by the client, transmitted on every registration, and honoured by the server: setting it to false produced an account in an activated state without the applicant demonstrating control of the address. The defect instantiates CWE-602, *Client-Side Enforcement of Server-Side Security*, and its proof is a single request. It is, however, unreachable by any procedure that does not possess the body schema, because the test consists of altering one named field among several and no enumeration strategy nominates that field. The field name is recoverable only from the invoking code. The same defect was subsequently confirmed on three distinct assets served by the same platform, which is reported in Section 6 as one defect rather than three findings.

**What would refute this.** The proposition is empirical and its scope is a property of servers, not a theorem, so the conditions under which it fails are worth stating rather than leaving to a reader to find. It fails on any server that distinguishes the two refusals observably: one that answers a malformed identifier with a different status code than an unauthorized one, or returns a validation envelope naming the offending field, or separates parse failure from authorization failure in a response the caller can see. Against such a server the assessor can detect the lower-right cell directly and the recovered encoding is a convenience rather than a precondition. The claim is that this distinguishability is absent often enough, and silently enough, that a procedure cannot assume it — not that it is impossible.

Two further conditions bound the proposition. It concerns routes whose authorization decision is reached through a parameter the caller supplies; a route taking no caller-supplied identifier has no encoding to get wrong. And it assumes the assessor cannot read the server, since source access would expose the parse-versus-authorize ordering directly, which is the concession of Section 2 restated at the level of a single request.

A corollary for reporting follows. Because the failure is silent, systematic and stable, a procedure that cannot exhibit a satisfied positive control for a given route should record the result for that route as *unmeasured* rather than as negative. The two are routinely merged, and the merge is what converts an absence of evidence into an apparent finding of security.

### 3.4 Equivalence of inferential structure with source inspection

| Property | Source inspection | Client recovery | Dictionary enumeration |
|---|---|---|---|
| Hypothesis comes from | the system's own source | the system's own client | an external wordlist |
| Falsifiable prior to transmission | yes | yes | no |
| Confirmation procedure | execution or test | contrasted request across subjects | response status |
| Informativeness of a negative | yes, scoped to inspected code | yes, scoped to recovered specification | limited to enumerated candidates |

Source inspection and client recovery share an inferential structure: inspect the system's own artefacts, derive a hypothesis the artefacts render falsifiable, then confirm empirically. Dictionary enumeration has a different structure, and the final row follows from that difference by definition rather than by measurement: a negative result for a path never enumerated is not a statement about the application. The table classifies inferential structure, not relative yield: which method surfaces more routes in practice is an empirical question whose answer would not bear on the validity argument this paper makes. The claim advanced is that client recovery occupies the first structure, not that it achieves the observability of source inspection.

A corollary follows. Client recovery and traffic observation are not substitutable. An observed session exposes only the code paths that session exercised, and deferred module loading entails that a given interaction session retrieves a fraction of the deployed client code. The corpus of Section 6 bears on the magnitude of this effect: across the targets for which both sources were collected, their route sets were very nearly disjoint. A procedure employing only one therefore carries a coverage gap that is substantial and, from within that procedure, unobservable.

## 4. Specification of the assessment procedure

Each stage exists because omitting it produced a specific failure that was observed rather than anticipated.

**Stage 1 — Edge characterization, per host.** Probe each host with a valid path and a non-existent control path, under multiple methods, comparing response bodies rather than status codes. This establishes three facts on which all subsequent inference depends.

*Does the status code carry the outcome?* On some hosts it does not: every request returns 200 and the failure is described inside the body, so a column of status codes records nothing. *Does the host answer uniformly?* A host that returns the same response to a real path and to a path that cannot exist is telling the assessor nothing about either, and a uniform answer is a property of one axis only — a host answering uniformly to every *path* may answer differently to a different *method*, which is why the probe varies both. *Does a command-line client reach the origin at all?* If the response is a bot-management interstitial, every subsequent measurement describes the intermediary rather than the application, and an instrumented browser is required before anything else is worth running.

A single characterization generalized across an estate is incorrect for at least one host in practice, so this stage is performed per host and recorded per host.

**Stage 2 — Subject establishment and positive controls.** Authorization propositions require a minimum of two subjects, verified distinct and verified live prior to testing. For each subject, establish a request returning substantive data and retain it as that subject's positive control.

**Stage 3 — Client artefact recovery, requiring no session.** Deployed bundles are public artefacts. The unauthenticated entry document, present in any application exposing a login, serves the runtime, the entry bundle, and in most cases the route manifest. Recover deferred modules by parsing the module map; where the map encoding does not conform to a recognized form, inspect the URL-construction function directly. An empty recovery constitutes a procedural failure, not an observation about the target.

**Stage 4 — Integration of observed traffic.** A capture of genuine product interaction contributes what bundles do not: routes of confirmed reachability with authentic request bodies. Given the corollary in Section 3.4, this stage is not discretionary; bundle recovery and traffic capture each cover surface the other omits.

**Stage 5 — Recovery of the specification rather than the path.** For each route, recover method, parameter identifiers, body schema, identifier encoding, authentication header, and the base-URL constant the invoking code concatenates the path onto. That last item is why a bare path is not yet surface: `/api/v1/me/profile` says nothing until it is known which host constant it is appended to, since the same string may belong to the application under test, to a vendor SDK bundled beside it, or to nothing reachable at all. A path whose base constant cannot be resolved is therefore classified as unresolved rather than counted. The invoking code, not the syntactic form of the path, is authoritative for every one of these attributes.

**Stage 6 — Inventory construction with provenance, and defence of the denominator.** Each route receives a record stating its source. Counting extracted string literals as attack surface overstates it: vendor SDK paths, lexical artefacts of embedded tooling, and unresolved bases are all superficially endpoint-shaped. The denominator must be stated and defended prior to any coverage assertion.

**Stage 7 — Selection for falsifiability.** Self-scoped routes exposing no tamperable identifier are overwhelmingly non-vulnerable and exhaust the request budget. Allocate requests where identifiers occur: path parameters, tenant and account parameters, nested child resources addressable by their own routes, export and reporting functions.

**Stage 8 — Data-plane instantiation prior to testing.** The isolation proposition concerns whether one subject retrieves another's data, and is not answerable while the second subject's account is unpopulated. Instantiate a small number of inert, uniquely marked records in every subject's account and retrieve them, since acknowledgement of ingestion does not establish persistence.

**Stage 9 — Contrast with pre-registered expectation.** State the expected outcome per subject per route prior to transmission. An expectation recorded subsequent to the response is rationalized rather than tested.

**Stage 10 — Request instrumentation.** Record route, method, acting subject, transmitted content, security-relevant response content, status, and the responding tier — edge or application. The design rule is that an attribute the assessor must remember to record will be omitted, while an attribute the instrumentation writes because the request happened will not.

The instrumentation has one structural gap, named here rather than left to be discovered. **It is keyed on the request, not on the finding.** Each row records what was sent and what came back, but nothing links a finished finding to the particular rows that evidence it, and nothing links an external decision about that finding back to either. Within a single assessment this costs little, because the rows can be resolved by hand. Across assessments it is the reason Section 6 declines to report external adjudication: the linkage that would let a reader check such a report was never written down, because no stage requires it. Writing a finding-level provenance key at the moment a draft first cites a row would close the gap, and it is the one amendment to this procedure the present work would recommend.

**Stage 11 — Escalation of demonstrated impact, not of induced effect.** Initial confirmation establishes that a boundary fails, not what an adversary obtains. Raise demonstrated impact until it cannot be raised with the available subjects, then terminate, and demonstrate reachability rather than exercising it: an enumeration and two retrievals, not bulk extraction.

## 5. Validity controls

These are not implementation details. Each one guards against a failure that this method makes *more* likely rather than less, for a single reason: a procedure that recovers surface quickly generates candidates quickly, and the rate at which candidates arrive is not the rate at which they can be checked.

**Control 1 — Positive control.** A test whose legitimate instantiation also fails has no discriminative power and establishes nothing. Prior to accepting any negative result, confirm that the legitimate path returned substantive data within the same batch. A negative result without a concurrent passing control constitutes absence of measurement rather than evidence.

**Control 2 — Tier attribution.** Refusal by an intermediary is not refusal by the application. A web application firewall rejection, a bot-management interstitial, and a rate-limit response occupy the same status field as an application decision and carry the opposite meaning. Every inference must record whether the request reached the origin.

**Control 3 — Boundary specification.** The crossed boundary must be named: subject to subject, tenant to tenant, role to role, unauthenticated to authenticated. Self-scoped effects, public data served over an interface, and client-side-only constraints are observations rather than findings. Every observation must therefore be filed with a verdict attached, because an observation filed without one grows more confident each time it is restated, while no new evidence is ever added.

**Control 4 — Identifier encoding derived from the invoking code.** This is Control 1 under a specific instantiation, argued in Section 3.3. A refusal on the owner arm is evidence concerning the request, not concerning the route.

**Control 5 — Acting subject derived from the transmitted credential.** An assessor who believes they are acting as the second subject while transmitting the first subject's credential invalidates every negative result measured within that slice, and no other element of the procedure detects the condition. Fingerprint the credential per request and record the derived subject identity rather than the asserted one.

A sixth practice is warranted by what it produces rather than what it prevents: a candidate the procedure invalidates constitutes a complete result. Recording the grounds of invalidation, with its evidence, is the output that preserves the credibility of the surrounding negative results.

## 6. Experience report

The procedure was applied to 45 authorized targets across 23 bug bounty programs. The figures below enumerate the procedure's own recorded outputs, and nothing in them asserts a judgment by any receiving programme. External adjudication of a subset of these outputs does exist, in the form of vendor-assigned vulnerability identifiers and programme awards; reporting it is deferred to separate work, because doing so credibly requires per-finding provenance linking each external decision to the specific artefacts that produced it, and this corpus does not carry that linkage.

| Procedural stage | Recorded output |
|---|---|
| Authorized targets with retained artefacts | 45, across 23 programs |
| Client artefacts recovered | 15,105 files |
| Routes inventoried with provenance | 5,652, across the 30 targets carrying an inventory |
| Routes recovered from client artefacts but absent from observed traffic | 1,375, on the 19 targets carrying both sources |
| Intersection of the client-recovered and traffic-observed route sets | 73, of a 3,805-route union |
| Requests transmitted and instrumented | 7,661 |
| Requests attributed to the application tier | 7,110 |
| Requests attributed to an intermediary tier | 83 |
| Requests whose responding tier was not determinable | 468 |
| Distinct acting subjects, derived from transmitted credentials | 94 identifiers |
| Typed lead records | 812, across 33 targets |
| Candidates invalidated by the procedure itself | 20 |
| Evidenced negative results recorded | 26 |
| Report drafts satisfying the procedure's internal severity gate and adversarial review | 13 |
| Distinct defects those drafts represent, after root-cause clustering | 11, across 10 targets |

Four rows are of principal methodological significance.

**Source intersection, and what it does not show.** On the nineteen targets carrying both a client-recovered and a traffic-observed route set, the two sets intersect in 73 routes of a 3,805-route union. Client recovery contributed 1,375 routes that traffic observation did not; **traffic observation contributed 2,357 that client recovery did not.** Traffic observation therefore yielded the larger unique contribution, by a wide margin, and the figures are stated in that order deliberately: the claim of this paper is non-substitutability, not client primacy. Nothing in the argument requires the client to be the richer source, and Section 3.1 asserts only that the client is a *recoverable* and *complete* specification of what the application itself invokes. The measurement on which Section 3.4's corollary and Stage 4's non-discretionary status depend is the near-disjointness, and that is what the intersection of 73 establishes. The figure is a set intersection over the complete inventories of those targets and involves no selection.

**Tier attribution.** Of 7,661 instrumented requests, 7,110 were attributed to the application tier, 83 to an intermediary, and 468 were not determinable from the record. Control 2 is thereby satisfied across the substantial majority of the corpus: the status codes underlying these figures describe application behaviour rather than a protective layer preceding it. A corpus unable to report this ratio could not support inference of any kind.

**Derived subject identity.** Ninety-four distinct acting subjects were derived by fingerprinting the credential present on each request rather than by accepting an asserted label. Control 5 is satisfied by construction: a slice transmitting an unintended subject's credential is observable in the record.

**Internally invalidated candidates.** Twenty candidates were invalidated by the procedure itself, alongside twenty-six separately recorded evidenced negative results. This figure distinguishes a method from an undisciplined candidate-generation procedure. A procedure recovering surface rapidly generates candidates rapidly, and the sole internal evidence that its gate exercises discrimination is a record of candidates the gate arrested. Eleven defects satisfied the gate; twenty candidates did not. One instance is worth stating because it shows the gate operating on the evidence layer rather than on judgment: a completed draft was withdrawn after audit established that its proof of concept asserted a status code and a response header for which no instrumented row existed.

Three qualifications apply. Provenance and lead-type attributes are free-text labels assigned by the procedure's own operators rather than values emitted by a calibrated instrument; no inter-rater reliability measure exists for them, and their categorial consistency is bounded by the consistency of the practice that produced them. The thirteen drafts resolve to eleven distinct defects because one defect was confirmed on three assets of a shared platform and one draft exists in two variants; reporting the draft count alone would treat one root cause as three results, which is the error the clustering column exists to prevent. And the eleven defects satisfied *this procedure's* severity gate and adversarial review, which are internal criteria, as stated at the head of this section.

### 6.1 Dictionary enumeration in this corpus

Dictionary enumeration was also executed against twelve hosts in this corpus, under soft-404 baselining and with rate-limited responses excluded, yielding 40 confirmed paths in total, thirty of them on a single host. On the one host where a dictionary scan and a client-recovered inventory exist for the same origin, the scan returned no confirmed path while the inventory held sixteen routes.

These figures are reported for completeness and support no comparison. The request budgets were not matched, the wordlists were curated per host rather than held constant, the twelve scanned hosts barely overlap the nineteen carrying both route sources, and scan effort was allocated by assessor judgment rather than by design. No inference about relative method yield should be drawn from them in either direction.

A controlled yield comparison is specifiable — a fixed target set, an identical per-target request budget, one wordlist held constant, the two methods executed independently, and the resulting route sets compared for unique contribution and for confirmed liveness under identical probing — and would be a worthwhile separate study. It is not required by any claim advanced here.

### 6.2 Extractor accuracy against published specifications, on three applications

Section 8 notes that the regex-based extractors dominating practice carry no published precision or recall evaluation [14]. That criticism applies to the extractor used here, and this subsection addresses it.

Two methodological commitments are taken from the literature on benchmarking vulnerability-detection tools, where both of the corresponding errors are documented [17]. Recall is trivially inflated by a rule that admits everything, so a recall figure is reported here only beside the precision of the same set and against a ceiling measured on the same artefact. And a ground truth that enumerates only what is known cannot establish absence, so a row the specification does not contain is reported as unmatched rather than as a confirmed false positive wherever the distinction is available; precision against a published specification is accordingly a lower bound rather than an estimate.

**Pre-specified reporting commitment, recorded before the measurement was taken.** The extractor is evaluated against a published OpenAPI specification serving as ground truth, on an open-source single-page application whose built client is publicly distributed. Precision — the proportion of extracted first-party routes that appear in the specification — is reported exactly as measured. A low value would not contradict the argument of this paper. It would quantify the limitation Stage 6 already asserts qualitatively, namely that extracted string literals are not automatically attack surface, and it would strengthen rather than weaken the case that the controls of Section 5 are necessary rather than advisory. A high value would support the reliability of the inventory on which Section 6's figures rest. Both outcomes are reported in the same terms.

Recall against the full specification is deliberately not reported as an accuracy figure. A client legitimately invokes only a subset of a published interface, so the specification is not a valid denominator for what the extractor should have found; such a ratio would measure the client's coverage of the API rather than the extractor's fidelity. Where a recall-shaped figure is given below it is labelled as specification coverage and carries no claim about extractor accuracy.

**Target and ground truth.** The evaluation used Jellyfin, an open-source media server whose maintainers publish an OpenAPI 3.0.4 specification, against the matching release of its single-page web client. The specification declares 294 paths at version 12.1.0; the client is the portable server distribution of the same version, comprising 986 minified and code-split JavaScript bundles totalling roughly 28 MB. Version alignment between specification and client is exact, which removes the most obvious confound in a comparison of this kind. Both artefacts are publicly distributed and the measurement involved no request to any running system.

**The structural premise, measured.** Of the 294 declared paths, 244 — 83.0 per cent — appear verbatim as literal strings in the distributed client bundles. Section 3.1 argues on structural grounds that the client must encode what a well-formed request requires; this figure is the first direct measurement of that premise offered here, and it supports it. The 50 absent paths are predominantly administrative and streaming-variant routes the web client does not invoke, which is the expected pattern: a client encodes the interface it uses, not the interface that exists.

**Extraction and classification fail separately, and on two of the three applications extraction is the larger loss.** The distinction matters because the tool emits two sets, not one, and only the second reaches an assessor. The **extraction set** is every path-shaped string the patterns recover from the bundles. The **API-shaped set** is the subset a classification heuristic then nominates as attack surface. A path can therefore be present in the first and absent from the second, and that is where this extractor loses most of the interface.

Both are measured against the same denominator. The specification declares 294 paths; 293 remain distinct once parameter placeholders are normalised on both sides, and 243 of those 293 are present in the client at all, which is the ceiling any extractor reading this client could reach.

Against that ceiling the extraction set reaches 240 of 243, or **98.8 per cent** — very nearly everything present. The API-shaped set reaches 23, or **9.5 per cent**. The heuristic discards about ninety per cent of the real interface that the extractor had already found. Expressed instead against the whole published interface rather than against the subset the client encodes, those 23 paths are 7.8 per cent of the 293; that second ratio is reported under the label committed to above, **specification coverage**, and carries no claim about extractor accuracy, since a client is not obliged to invoke every route a server offers. Precision on that set is correspondingly poor. The set contains 73 rows, of which 24 appear in the specification: **32.9 per cent**, and that is the headline figure, because it describes the set as the tool actually emits it.

*The 73 rows decompose as follows.* Eleven are absolute third-party URLs — documentation links, a React Router upgrade notice, a Google cast loader, a map search endpoint — every one a false positive. Setting those aside as out of scope for first-party surface leaves 62 relative paths of which 24 match, giving 38.7 per cent; that variant is reported for completeness and is not the figure quoted elsewhere in this paper. The 24 matching rows resolve to 23 distinct normalised paths, because `/Users` and `/Users/` are both emitted, which is why precision is computed over rows and recall over distinct paths and the two figures differ by one.

*The 38 false positives decompose further.* Thirty-five fall into one identifiable class: client-side router paths such as `/dashboard/users/:userId/:tab` and `/login`, which are views rather than server endpoints. Excluding that single class raises precision to 24 of 27, or **88.9 per cent**, and leaves three unexplained false positives — `/Download`, `/Password` and `/RemoteImages/Download` — all path fragments consistent with string concatenation, each being the tail of a longer specification route. Because the router class was identified by inspecting the misses rather than defined in advance, 88.9 per cent is a decomposition of the measurement and not an independent result. These three rows are ones the tool nominated that the specification does not contain, and they should not be confused with the three specification paths the tool missed entirely, which are a different set of the same size: `/branding/css.css`, `/collections` and `/trailers`.

**Interpretation, in the terms committed to above.** On Jellyfin the failure is not extraction but classification: the extractor recovers very nearly everything present, and its heuristic then discards about ninety per cent of the real interface while admitting a comparable volume of client routes that are not server endpoints. The heuristic is wrong in both directions at once. That converts the warning of Stage 6 — extracted string literals are not automatically attack surface, and the denominator must be defended rather than assumed — from a cautionary remark into a measured property of a working extractor, and it sharpens Section 5: no coverage claim computed over a set that is 32.9 per cent precise and 9.5 per cent complete can be trusted on its own, so the controls that make an individual negative interpretable are not advisory.

Two consequences for practice follow, neither of which bears on the validity argument of Section 3.3, since that argument concerns what a recovered specification entitles an assessor to conclude once a route is under test rather than how the route was nominated. Where a specification or a served sourcemap exists, classification should be performed against it rather than by a shape heuristic, which inverts the usual assumption that extraction is the hard part. And in the absence of ground truth the full extraction set, not its API-shaped subset, is the defensible candidate pool, the subset having been shown to exclude most of the real interface.

**Applying this result to the corpus figures of Section 6.** The inventory figures earlier in this section were produced by the same extractor now measured, so the measurement bears on them and the arithmetic should be done here rather than left to the reader. If the client-derived portion of the corpus carries precision of the order measured above, the 1,375 routes attributed to client recovery alone correspond to a substantially smaller number of real routes — on the order of four hundred and fifty under a direct application of the 32.9 per cent figure, or five hundred and thirty under the 38.7 per cent variant. The traffic-observed portion is not subject to the same correction, because those routes were observed being requested and are real by construction.

The principal conclusion survives this correction, and survives it for a structural reason rather than a numerical one. The intersection of the two sources is 73 routes. Correcting the client-derived set downward cannot increase that intersection, and the traffic-derived set is uncorrected, so near-disjointness holds under any correction of this kind and holds more strongly the larger the correction. What the correction does affect is any reading of the raw counts as a measure of how much surface each source contributes in absolute terms, and such a reading should not be made.

Two cautions bound the transfer itself. The precision figure was measured on one extractor run against one application, and the corpus inventories were additionally curated by operators rather than emitted directly by the tool, so applying the figure across targets is an approximation and not a measurement. And the corrected count is offered as an order of magnitude, not an estimate with any claim to precision of its own.

**A repaired classifier, measured on three applications.** The diagnosis above localises the failure to classification, which is actionable, so the classifier was rewritten and evaluated on three applications: Jellyfin, and two held out — Zulip Server 12.3 and Immich v3.2.4, each with its specification and client taken from one release tag. The keyword allowlist was replaced by call-site evidence: a path is admitted when the surrounding code passes it to an HTTP client or attaches a method to it, excluded when the surrounding code is navigation rather than request construction — a link target, a `navigate` call, a route-constant array — and otherwise retained, because discarding on absence of evidence is what produced 9.5 per cent recall. Jellyfin is the application the diagnosis came from and is not held out; Zulip and Immich are. Thresholds were fixed before measurement on each held-out application and both pre-registration files ship in the reproduction package. No pre-registration exists for Jellyfin, which bears on the tier result below, since the application where the tier separates most strongly is the one that was not held out. One criterion is applied to all three applications: **primary**, the repaired classifier's recall reaches at least 90 per cent of the measured extraction ceiling; **secondary**, precision over the set as emitted falls by no more than 5 points. A ceiling-relative primary is the correct form, because an absolute point-gain requirement would be imposed on a quantity bounded by a ceiling that differs per application.

**One result generalizes, and it is the admission half.** On all three applications the repaired classifier's recall equals the extraction ceiling exactly: 98.8 per cent of 243 present paths on Jellyfin, 62.2 per cent of 90 on Zulip, 82.8 per cent of 192 on Immich. The primary criterion is met at 100 per cent of the ceiling in every case. This is the same effect the Jellyfin measurement already identified and not a stronger one: the repaired rule admits essentially everything the extractor recovers, so the gain is the consequence of no longer rejecting rather than of classifying better.

**The precision effect is application-dependent and can be strongly negative.** Precision over the set as emitted falls 13.3 points on Zulip, from 34.0 to 20.7 per cent, and rises 12.4 points on Jellyfin, from 32.9 to 45.3 per cent; measured with absolute third-party URLs set aside the Jellyfin pair is 38.7 to 62.4 per cent. The direction tracks how many non-route rows the extractor emits on a given client: the repaired rule admits 149 absolute third-party URLs of 545 rows on Jellyfin against 11 of 73 before, and an assessor using this output needs a host filter before the set is usable. The secondary criterion is therefore met on Jellyfin and missed on Zulip. Under the single criterion the verdicts are **generalized on both axes** for Jellyfin and **partially generalized** for Zulip.

**Immich is a valid test of the ceiling and an invalid test of both precision and the tier.** Its web client carries no URL literals; the paths exist only inside `@immich/sdk`, which is code-generated from the same specification used here as ground truth. Every path string in the measured artefact therefore originates in the ground truth, and the resulting precision figures — 98.4 per cent for the original classifier and 98.8 for the repaired one — measure the generator rather than the classifier. **The secondary criterion is not assessable on Immich** and its precision figures are not comparable with the other two applications. The ceiling figure stands, because it is not circular: a specification cannot determine which paths a regular expression recovers. The tier figures do not, for a reason that follows from the same circularity and is given with the tier table below.

This is the clearest case in the evaluation for the second ground truth identified in Section 9. Immich's precision is unmeasurable against its own specification and would become measurable against its server's route declarations, which the generator does not consume.

**The evidence tier is not a general operating point.** The repaired version reports an evidence tier per route. A route is assigned one of four tiers — request-construction, structural, absent-evidence and navigation, which the shipped rule emits under the labels `request-construction`, `structural`, `none` and `router-definition` respectively — and the spread is defined as the request-construction tier's precision minus the absent-evidence tier's, against a stated bar of 20 points for the tier to be said to carry signal.

| Application | request-construction | structural | absent-evidence | navigation | spread | ordering |
|---|---|---|---|---|---|---|
| Jellyfin 12.1 | 91.1% (112 rows) | 51.5% (33 rows) | 51.0% (251 rows) | 0.0% (28 rows) | **+40.1** | monotone |
| Zulip 12.3 | 28.6% (28 rows) | 36.2% (177 rows) | 19.4% (62 rows) | — | **+9.2** | **inverted** |
| Immich 3.2.4 | not assessable | not assessable | not assessable | — | — | — |

The navigation tier is the one unambiguous success and it is a success at exclusion rather than at admission: on Jellyfin it collects 28 rows and not one of them is a server route, so the rule that recognises a path as a view rather than a request is correct every time it fires. That is a useful filter and it is not an operating point, because it tells an assessor what to *discard*, never which of the remainder to trust.

The spread understates the problem on Zulip, where the ordering inverts: the structural tier at 36.2 per cent stands above request-construction at 28.6, so the tier is not even monotone in the strength of the evidence it records. On Jellyfin the ordering holds. On Immich the tier is not assessable for the same circularity that invalidates its precision: a tier separates routes from false positives, and that artefact yields one false positive among 167 relative rows — the base path `/api` itself — against 177 of 424 on Jellyfin, so with nothing to discriminate every tier sits between 97.5 and 100 per cent precision and the spread is zero by construction rather than by measurement.

The tier is therefore a strong precision signal on one of the two applications where it can be assessed, and on the other it is both weak and inverted. It cannot be offered as a general way to choose an operating point without calibrating it per application, which is what an operating point is supposed to spare an assessor from doing.

**The extraction ceiling, and why it differs by client idiom.** The ceilings are 98.8, 62.2 and 82.8 per cent, so on two of three applications the extractor fails to recover between a sixth and two fifths of the interface literally present in the client. Reading every unrecovered path on Immich gives two causes and no unexplained residue: 27 of 33 are template literals whose interpolation contains a nested object, as a generated query-string helper emits, and 6 carry two or more interpolations. Both reduce to one mechanism. Neither relative-path pattern can span a template interpolation whose contents are non-trivial: the character class in the plain-path pattern contains no parenthesis, so any interpolation holding a function call breaks the match, and the template pattern tolerates one interpolation of at most sixty characters containing no closing brace, which a query-string builder exceeds. Jellyfin is unaffected because its bundles carry literal `{itemId}` braces rather than interpolations — which is the whole difference between 98.8 and 82.8 per cent, and the reason the ceiling is a property of client idiom rather than of the interface.

A character class cannot express balanced delimiters, so widening it would admit arbitrary code into path strings. The correct fix is a scanner that consumes a quoted string while tracking interpolation nesting depth and replaces each complete interpolation with a placeholder. **It is proposed here and not applied**, so that the prediction can be recorded rather than confirmed after the fact: applying it should move Immich's ceiling from 82.8 per cent to approximately 99 per cent, every residual path being accounted for by the two causes above, and should leave Jellyfin's ceiling essentially unchanged.

**Composition of the remaining false positives.** Of 149 false positives among relative paths in the repaired Jellyfin run — a count that coincides with the number of absolute third-party URLs that run emits and denotes a disjoint set — 24 are client router paths the navigation rule did not catch and 125 are other. A minority of those are categorically not server routes: static asset paths, one unevaluated template expression, opaque fragments. Whether that noise drives the result was tested rather than assumed — excluding every string containing template syntax, whitespace, markup characters or a static-asset extension before measuring changes precision by less than one point on both runs. The residual is dominated by path fragments produced by string concatenation, some of which are prefixes of real routes; `/RemoteSearch/Subtitles/` is one, a genuine route segment the specification lists only in its full form. This is why precision against a published specification is a lower bound rather than an estimate.

**Scope of this evaluation.** It covers one extractor against three applications, each with **one** ground-truth artefact — its published specification — so the error contributed by the choice of ground truth is unbounded here; Section 9 identifies a second, independent ground truth derivable from each server's own route declarations as the first correction this evaluation needs. No comparison against the practitioner extractors this work is positioned against is reported, for the reason given in Section 7. And the corpus figures earlier in Section 6 were produced by the original classifier and are left unchanged, because restating them under a later tool would describe a corpus that was never assessed that way.

Reproduction materials accompany this manuscript in three sibling directories — `validation/` for Jellyfin, `validation-zulip/` and `validation-immich/` — each holding its specification with a digest, the output of both classifiers, and a `VALIDATION.json` listing every figure beside the version-pinned download URL and a content digest of the extracted client. The two held-out packages each additionally hold the pre-registration recording their thresholds. `validation/` holds the two comparison scripts and `classifier_rule.py`, which carries both classification rules lifted verbatim from the extractor with a self-test showing each failure direction. `reproduce_precision.py` takes a run directory, a specification and an optional base-prefix strip, and regenerates every precision, coverage and tier figure in this subsection for either classifier on any of the three applications; the tier table is computed by applying `classifier_rule.py` to the evidence fields recorded for every extracted route, so the two runs of one application yield the same table. Client archives are not identified by their own digests, because one of the three re-compresses server-side and returned different archive hashes for the same pinned URL; the recorded digest is taken over the extracted file set instead, each file contributing its repository-relative path followed by the SHA-256 of its bytes, ordered by path. `reproduce_recall.py` requires the client bundles, which are not redistributed because they are the other projects' code and two of the three are copyleft; it prints the pinned URL and the expected digest and exits rather than proceeding without them.

## 7. Threats to validity

**Construct validity.** The provenance and lead-type attributes operationalize their constructs through operator-assigned free-text labels, not through instrumented classification. The severity gate and adversarial review are internal criteria whose correspondence to any external standard is unestablished. Tier attribution and derived subject identity are instrument-emitted and are correspondingly stronger. The inventory construct is now partly measured rather than assumed: Section 6.2 reports the precision and completeness of the heuristic that populates it, and both are poor. It also works through what that implies for the corpus counts, including the correction it forces and the reason the non-substitutability conclusion is unaffected by it. Two bounds on that construct are weaker than a single number suggests. The completeness bound is set by extraction rather than classification and varies with client idiom — the measured ceilings are 98.8, 62.2 and 82.8 per cent across three applications — so a coverage figure computed over this inventory should be read against the ceiling of the client it came from, which for the Section 6 corpus was not measured. And the repair postdates the corpus and was not applied to it, so the construct bounding the Section 6 figures is the original classifier, not the improved one.

**Internal validity.** Two distinct comparisons are absent and they are not absent for the same reason, so they are separated here rather than conceded together.

The first is a *yield* comparison for the field procedure, against dictionary enumeration or against unassisted manual assessment. The experience report incorporates no such control condition and does not establish that equivalent outputs were unobtainable by other means. This one is deliberate. The central contribution of Section 3.3 is a validity argument, resting on the observational equivalence of a malformed request and an enforced boundary together with demonstrated instances of that failure, and a yield measurement would not strengthen it; the design such a study would require is specified in Section 6.1 and the inferences it would license are not claimed here. What the report establishes is that a procedure built on the argument executes at scale against production systems and that its gate arrests a portion of its own output.

The second is an *accuracy* comparison for the instrument, against the practitioner extractors this work is positioned against. That absence is a genuine weakness rather than a scoping decision. The measurement in Section 6.2 establishes how the extractor performs against ground truth but not whether it performs better or worse than the tools in common use, and because those tools publish no accuracy figures [14], the comparison cannot be made by reading. It is specifiable, it requires no running system, and it is the first item of future work in Section 9 for that reason.

**External validity.** The report documents a single operator's record, produced by the procedure under study rather than by an independent instrument, across 45 targets selected by programme availability rather than by sampling design. Generalization to other operators or target populations is unsupported.

**Ecological validity.** The targets are production systems under authorized assessment, and the recorded responses are genuine. This constitutes the report's principal methodological strength and is the dimension on which benchmark evaluations are weakest.

**Scope conditions.** The argument is delimited to interface-constituted vulnerability classes and does not extend to classes requiring implementation observability: injection reaching a query constructor, unsafe deserialization, memory-safety defects, and invariant violations internal to a transaction. The structural precondition of Section 3.1 fails for applications that are not client-rendered, that construct requests server-side, or that expose their interface solely through a native client.

**Sufficiency of the controls.** The controls of Section 5 are necessary but not sufficient. They preclude identified invalidating conditions. They do not establish that a negative result is correct, only that it is not void for an enumerated reason.

## 8. Relation to prior work

**Endpoint recovery from client code is established prior art, and this paper does not claim it.** Sigalov and Gamayunov set out the problem in the terms used here — determining a server's HTTP endpoints is revealing its attack surface, and the client is where that surface can be inferred — and state the priority claim for inferring server endpoints from client-side JavaScript by non-trivial static analysis [5,6]. Their critique of the alternative is the same as Section 3.4's: dynamic crawling fails wherever the request-sending code cannot be triggered through interface interaction. Their observation that a single page of a single-page application frequently references the entire endpoint set is the empirical counterpart of the structural argument in Section 3.1. Wittern and colleagues treat the static analysis of API request construction in JavaScript as a software-engineering problem [7]; Gelato combines static and dynamic analysis for client-side security assessment [8]. In practice the extraction step is performed by regular-expression scanners over client bundles, of which LinkFinder is the most widely adopted; it carries no accompanying publication and no published precision or recall evaluation [14], which is the gap Section 6.2 addresses for the extractor used here.

**The testing literature assumes the specification this paper recovers.** RESTler fuzzes a REST interface by inferring producer–consumer dependencies among request types *from its specification*, and analyses dynamic feedback to prune invalid sequences [9]. Barabanov and colleagues detect candidate IDOR and BOLA conditions by processing an OpenAPI specification and mapping systematized attack techniques onto its properties [10]. AuthProbe drives multi-identity authorization tests from an OpenAPI specification and confirms a leak by comparing the response against a ground-truth fetch performed by the true owner [13] — which is an independent instance of the positive control required in Section 5. In each case the specification is an input. Where no specification is published, which is the ordinary case for a deployed web application, that input has to be produced, and the properties of the artefact produced then govern what the test can establish. This paper is about that step and its consequences, not about the test strategy applied afterwards.

**The adjacent indistinguishability claim is a different one.** AuthProbe states that the defining feature of this flaw class is that a malicious request is byte-for-byte indistinguishable from a legitimate one, which is why firewalls and single-identity scanners fail to detect it [13]. That is a claim about *detection by a defender*, and it is resolved by acting under two controlled identities. The claim in Section 3.3 is distinct and is not resolved that way: a *malformed* request is observationally indistinguishable from an *enforced boundary*, so the failure survives any number of identities, because every arm of the contrast is malformed together. Multi-identity testing is necessary and is not sufficient; the recovered encoding is what makes the contrast interpretable at all.

**Where the empirical literature on this flaw class sits.** BolaRay studies 101 real-world instances in open-source applications and combines SQL with static analysis to infer object-level authorization models and verify their enforcement, reporting 193 true vulnerabilities across 25 applications at a 21.86 per cent false-positive rate [11]. That is a white-box method and it establishes what source observability permits; it is the comparison point for Section 2's concession rather than a competitor to it. On the black-box side, an empirical taxonomy of 107 classified bug-bounty disclosures reports that the literature on this class remains almost entirely conceptual, and reports distributions over identifier format among other attributes [12] — independent field evidence for the dependency Section 3.3 argues from, and a preprint rather than a peer-reviewed result.

What that literature supplies is the extraction technique. What it does not address is the question this paper takes up: given a recovered interface specification, what can and cannot be established with it, and under what conditions is a result measured against it valid. Three contributions follow from that question.

First, the sufficiency argument of Section 3.2 delimits the vulnerability classes for which the specification substitutes for the implementation, and concedes the classes for which it does not. The prior work establishes that endpoints can be recovered; it does not establish what recovery entitles an assessor to conclude.

Second, and principally, Section 3.3 identifies a measurement-validity consequence that the extraction literature does not treat: the recovered specification determines request well-formedness, and a malformed request is observationally indistinguishable from an enforced authorization boundary. A procedure that recovers paths without recovering identifier encodings and body schemata will therefore generate negative results that are void rather than informative, and will not detect that this has occurred. This is a claim about the validity of measurement rather than about the yield of discovery, and it is the paper's principal contribution.

Third, the validity controls of Section 5 and the field report of Section 6 address a gap the practitioner tooling leaves open: the regex-based extractors dominating practice have no published precision or recall evaluation [14]. Section 6.2 supplies one for the extractor used here, against a published specification as ground truth, and the result is unflattering in a specific and informative way — on Jellyfin, near-complete extraction paired with a classification heuristic that is 32.9 per cent precise and 9.5 per cent complete. Reporting it is the point: a paper arguing that measurement validity is the neglected problem in this area cannot leave its own measuring instrument unmeasured. The diagnosis was also actionable, and acting on it is what bounds the claim: replacing the keyword heuristic with call-site evidence and measuring both rules on three applications shows one effect that generalizes, recovery of the full extraction ceiling, and two that do not, precision and the evidence tier. The three applications also relocate the larger loss from classification to extraction on the two clients that build paths at runtime. Both rules and all six runs ship with this manuscript so that each claim can be checked rather than believed.

Separately, work on language-model agents demonstrates exploitation of known one-day vulnerabilities [1] and multi-agent operation against zero-day targets [2], in both cases with access to the code under assessment, and agent frameworks for penetration testing report subtask completion against hosts rather than against web interfaces [15]. These motivate the opening question of Section 1 — what substitutes for readable code when the server is not disclosed — rather than bearing on the answer.

The consequence of Section 3.3 does, however, bear directly on how such systems are evaluated. A review of benchmarking practice across eighteen prototypes in this area finds the field short of baselines and of comprehensive metrics, and questions whether capture-the-flag testbeds represent real engagements [16]. An agent assessed on a web target it cannot read is in the position described here: unless the interface encoding it transmits was recovered rather than guessed, its failures to exploit are void rather than informative, and no completion rate computed over them is interpretable. A benchmark that does not record whether each probe was well-formed cannot distinguish an agent that was refused from an agent that was never understood.

## 9. Conclusion

Assessment is effective against source code because the implementation is observable, and this holds whether the assessor is a reviewer, a scanner or a language-model agent — the property belongs to the artefact, not to the reader. Web applications do not expose their implementation, but they do expose their interface specification, since the client invoking that interface is distributed in its entirety to every user agent and must encode whatever a well-formed request requires. Source inspection and client recovery therefore answer distinct questions, and no equivalence is claimed.

The claim advanced is that the question client recovery answers is the one determinative for the vulnerability classes the standard interface taxonomy ranks highest. Broken object level authorization (API1:2023, CWE-639), broken object property level authorization (API3:2023, CWE-915), broken function level authorization (API5:2023), sensitive business flow access (API6:2023), and behavioural workflow enforcement failure (CWE-841) are determined by what a server accepts from a caller. For these the interface specification is sufficient, the confirming evidence is a request together with a subject contrast, and the specification recovered from the invoking code is what renders the request well-formed — which is equally what renders a negative result informative. Neither recovery nor validity is the easy half. Section 6.2 measures extraction ceilings of 98.8, 62.2 and 82.8 per cent across three clients, so recovery is itself incomplete wherever a client builds its paths at runtime, and the validity controls are what prevent the volume that is recovered from constituting high-confidence false positives. The clearest internal evidence of their operation is the record of candidates the procedure declined to advance.

**Future work.** Five extensions follow from the limitations stated in Section 7, in the order in which they would strengthen the argument.

*A baseline comparison.* The extractor is measured here against ground truth but not against the practitioner tools it is meant to improve on, and those tools have no published accuracy figures of their own [14]. Running LinkFinder and a parser-based alternative over the same three clients against the same specifications, under one normalisation, would convert the criticism in Section 8 into a measurement and supply the baseline that reviews of evaluation practice in this area call for [16]. It requires no access to any running system.

*A second, independent ground truth per application.* Each application is evaluated here against one artefact, its published specification. All three are open source, so a second ground truth is derivable from the server's own route declarations, and agreement or disagreement between the two would bound the error the choice of ground truth contributes. On the application whose client is code-generated from the specification, this is the only route by which precision becomes measurable at all.

*Confirmation of liveness.* A path present in a specification is not necessarily a route the deployed server answers. Standing each application up from its published container image and probing every extracted path under a single identity would replace the predicate *appears in the specification* with *answers on the wire*, which is the predicate an assessor acts on.

*The interpolation-aware scanner.* The fix stated in Section 6.2 is deliberately left unapplied so that its prediction stands rather than being confirmed after the fact: implementing it should move the lowest ceiling from 82.8 to approximately 99 per cent and leave the highest essentially unchanged. The prediction is falsifiable and the test is cheap.

*Independent execution.* Every figure reported here was produced by the operator who built the procedure. The reproduction package exists so that this is remediable rather than merely conceded, and an independent re-measurement, including one that disagrees, would establish more than any further measurement by the same hand.
